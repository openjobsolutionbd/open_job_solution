# AGENTS.md

এই ফাইলটা যেকোনো AI এজেন্ট/টুলের জন্য (Claude, ChatGPT/Codex, Cursor, Copilot ইত্যাদি) — এই রিপোতে কাজ করার আগে এটা পড়ে নিন।

## ⚠️ প্রথম ধাপ — যেকোনো কাজ শুরুর আগে বাধ্যতামূলক

**`bash scripts/session_status.sh` চালান — এটাই সবার আগে করুন, অন্য যেকোনো কিছুর আগে।**

কারণ: ব্যবহারকারী নিয়মিত **একাধিক Claude অ্যাকাউন্ট এবং একাধিক চ্যাট থেকে একই সময়ে এই রিপোতে কাজ করান**, এবং প্রায়ই একই চ্যাটের আগের কোনো মেসেজে ফিরে গিয়ে (edit করে) নতুন কাজ শুরু করেন। এর ফলে —
- local sandbox-এর অবস্থা কথোপকথনের এই মুহূর্তের সাথে নাও মিলতে পারে (আগের কোনো abandoned branch-এর bash কমান্ড সত্যিই ডিস্কে চলে গিয়ে থাকতে পারে)
- অথবা এটা সম্পূর্ণ নতুন sandbox/অ্যাকাউন্ট হতে পারে যেখানে repo এখনো ক্লোনই হয়নি
- অথবা অন্য কোনো অ্যাকাউন্ট/চ্যাট ইতিমধ্যে নতুন কমিট push করে থাকতে পারে

**একমাত্র জিনিস যেটা সবসময় নির্ভরযোগ্য তা হলো GitHub-এর remote অবস্থা** — local মেমরি বা কথোপকথনের আগের অংশে যা মনে হচ্ছে তার উপর ভরসা করে কাজ শুরু করবেন না। `session_status.sh` remote ফেচ করে, local-remote তুলনা করে, এবং working directory-তে কোনো stray/অসম্পূর্ণ পরিবর্তন আছে কিনা দেখায়। এতে সমস্যা দেখালে (remote এগিয়ে, বা অপ্রত্যাশিত uncommitted পরিবর্তন) আগে সেটা ব্যবহারকারীকে জানান ও সমাধান করুন, তারপর নতুন কাজ শুরু করুন।

repo এখনো ক্লোন করা না থাকলে (প্রথমবার এই sandbox-এ) —
```bash
git clone https://github.com/openjobsolutionbd/open_current_affairs.git
cd open_current_affairs && bash scripts/session_status.sh
```

## প্রজেক্ট সংক্ষেপে

**Open Current Affairs** — টপিক-ভিত্তিক বাংলা কারেন্ট অ্যাফেয়ার্স knowledge-base। প্রতি মাসে নতুন তথ্য দিয়ে `docs/topics/`-এর পেজগুলো আপডেট হয়। Cloudflare Pages দিয়ে হোস্ট করা static website (build output: `docs/`)।

বিস্তারিত পরিচয়ের জন্য `README.md` ও `PROJECT.md` দেখুন। এই ফাইলে শুধু এজেন্ট-নির্দিষ্ট নির্দেশনা ও সতর্কতা আছে।

## টোকেন-সাশ্রয়ী অভ্যাস

এই রিপোর মালিক নিয়মিত একাধিক Claude সেশন দিয়ে কাজ করান, তাই দক্ষতা গুরুত্বপূর্ণ — তবে **নির্ভুলতা/মান কমিয়ে নয়়**, শুধু অপ্রয়োজনীয় পুনরাবৃত্তি এড়িয়ে:

- push-এর আগে fetch/log/build/verify আলাদা আলাদা কমান্ডে না চালিয়ে `bash scripts/preflight.sh` একটাই কল দিয়ে চালান।
- ডুপ্লিকেট টপিক চেক করতে পুরো `archive/*.md` বা সব `docs/topics/*.md` `grep`/`view` না করে `bash scripts/check_topic.sh` ব্যবহার করুন — শুধু আসল মিল পেলেই সেই একটা ফাইল `view` করুন।
- কোনো ফাইল edit করার পরপরই পুরো ফাইল আবার `view` করে "যাচাই" করার দরকার নেই — `str_replace`/`create_file`-এর সফল রেসপন্সই যথেষ্ট প্রমাণ; শুধু জটিল/multi-step edit-এর ক্ষেত্রেই ফের `view` করুন।
- বড় ফাইল (যেমন `archive/*.md`, `docs/topics-index.json`) পুরোটা `view` করার বদলে নির্দিষ্ট অংশ দরকার হলে `grep -n` বা `view_range` ব্যবহার করুন।
- একাধিক ছোট bash কমান্ড আলাদা আলাদা কল না করে `&&`/`;` দিয়ে একসাথে একটা কলে চালান, যেখানে যুক্তিসঙ্গত।
- **কী কমাবেন না:** ছবি থেকে টপিক তৈরির সময় ব্যবহারকারীকে extract করা তথ্য দেখিয়ে নিশ্চিত হওয়া, কমিটের আগে `git diff` দেখানো, এবং বাংলায় বিস্তারিত কমিট মেসেজ লেখা — এগুলো ভুল/ডেটা-লস প্রতিরোধ করে, তাই টোকেন সাশ্রয়ের জন্য এড়ানো উচিত না।

## কনটেন্ট এডিট করার আগে

- **সাধারণ নিয়ম — একই বিষয় (টপিক) যেখানেই পাওয়া যাক, merge করুন, নতুন আলাদা টপিক বানাবেন না:** ম্যাগাজিন/সোর্সে একই বিষয়ের তথ্য একাধিক জায়গায় (একাধিক বিভাগে, একই সংখ্যায় বা ভিন্ন সংখ্যায়) থাকা স্বাভাবিক। কোনো নতুন `docs/topics/*.md` টপিক লেখার আগে (বা MCQ-এর তথ্য existing টপিকে বসানোর সময়, দেখুন "MCQ হ্যান্ডলিং") যাচাই করুন সেই বিষয় ইতিমধ্যে কোনো existing টপিক ফাইলে আছে কিনা। থাকলে আলাদা নতুন টপিক না বানিয়ে সেই existing টপিকেই তথ্য merge/আপডেট করুন (নতুন তথ্য "পরিবর্তনের ইতিহাস"-এ এন্ট্রি দিয়ে) — পাশাপাশি দুইটা প্রায়-অভিন্ন টপিক রাখা যাবে না। এই সিদ্ধান্ত সবসময় নিজে পড়ে-বুঝে নিন, কখনো script/regex/প্যাটার্ন-ম্যাচিং দিয়ে স্বয়ংক্রিয়ভাবে না (ভুল জায়গায় merge বা ভুল ডুপ্লিকেট-শনাক্তির ঝুঁকি আছে)।
  - **এটা `docs/ghotonaprobaho/` ও `docs/top-news/`-এ প্রযোজ্য না** — ওগুলো তারিখ-ভিত্তিক ইতিহাসের লগ; একই বিষয় নিয়ে ভিন্ন তারিখে আলাদা আলাদা খবর আসা ডুপ্লিকেট না, বরং প্রতিটাই আলাদা ঘটনা হিসেবে সংরক্ষণযোগ্য। এই দুই ফোল্ডারের জন্য existing নিয়মই (একই তারিখ-হেডিং-এর নিচে ডুপ্লিকেট-চেক, আর সংলগ্ন রেঞ্জ হলে `git mv` দিয়ে rename) বহাল থাকবে, উপরের ফাইল-কাঠামো টেবিলে ও "সঠিক গন্তব্যে বসানো" অংশে যেমন লেখা আছে।
- **নতুন টপিক বানানোর আগে `bash scripts/check_topic.sh "কীওয়ার্ড"` চালিয়ে ডুপ্লিকেট চেক করুন** — এটা কমপ্যাক্ট `topics-index.json` গ্রেপ করে, তাই `docs/topics/*.md` বা `archive/*.md` (যা হাজার+ লাইনের raw মাসিক সোর্স) পুরোটা পড়ার দরকার হয় না। মিল পেলে সেই টপিক ফাইলটাই শুধু `view` করে দেখুন আসলে ডুপ্লিকেট কিনা (এই রিপোতে আগে ডুপ্লিকেট টপিক তৈরি হওয়ার ঘটনা ঘটেছিল, পরে মার্জ করতে হয়েছিল)।
- ফ্রন্টম্যাটারে `title`, `tags`, `last_updated` (ফরম্যাট: `YYYY-MM` বা `YYYY-MM-DD`) সঠিক রাখুন — সার্চ ইনডেক্স এগুলোর উপর নির্ভর করে।
- ফাইলনামই স্লাগ (`[a-z0-9]+(-[a-z0-9]+)*` প্যাটার্ন) — আলাদা slug ফিল্ড নেই।
- ঘটনাপ্রবাহ ফাইলে টপিক-লিংক দিতে দুইটা ফরম্যাটই বৈধ: লাইনের একদম শেষে শুধু `[[slug]]` (পুরো লাইনটাই তখন একটা টার্ম), অথবা একই লাইনে একাধিক আলাদা টপিক লিংক করতে `[[বাক্যাংশ|slug]]` (একই লাইনে যতগুলো দরকার ততগুলো বসানো যায়; দুই ফরম্যাট একসাথে একই লাইনে মেশানো যাবে না — `|` থাকলে সেটাই প্রাধান্য পায়)। উভয় ক্ষেত্রেই `slug` অবশ্যই বিদ্যমান কোনো টপিকের সাথে মিলতে হবে, নাহলে build ভেঙে যাবে (ইচ্ছাকৃত ভ্যালিডেশন)।

## কনটেন্ট এডিট করার পর

```bash
pip install pyyaml --break-system-packages   # প্রয়োজনে
python3 scripts/build_index.py
python3 scripts/verify_site.py
```

`build_index.py` `docs/topics-index.json`, `docs/ghotonaprobaho-index.json`, `docs/top-news-index.json`, `docs/sw.js`, `docs/version.json` রিজেনারেট করে এবং ভ্যালিডেশন এরর থাকলে non-zero exit code দিয়ে থামে। `verify_site.py` এর পরে চলে এবং পুরো সাইট জুড়ে ক্রস-চেক করে — এই দুটোই push-এর আগে **লোকালি অবশ্যই** চালাতে হবে (ঐচ্ছিক নয়)। **GitHub push করলে `.github/workflows/update-wiki.yml` দুটোই স্বয়ংক্রিয়ভাবে চালায়** এবং `verify_site.py` fail করলে generated output commit/push হয় না — কিন্তু তার মানে এই না যে লোকাল চেক বাদ দেওয়া যাবে, কারণ লোকাল fail ধরা পড়লে ব্যবহারকারীকে ভাঙা diff দেখানো এড়ানো যায়।

## ওয়ার্কফ্লো: স্ক্যান করা ম্যাগাজিন সংখ্যা থেকে কনটেন্ট যোগ করা

ব্যবহারকারী মাঝেমধ্যে "প্রফেসর'স কারেন্ট অ্যাফেয়ার্স"-এর মতো মাসিক ম্যাগাজিনের স্ক্যান করা পেজ (সাধারণত `.zip`-এ অনেকগুলো `.jpg` পেজ) আপলোড করে সেখান থেকে কনটেন্ট বের করে এই রিপোতে যোগ করতে বলেন। নিচের ধাপগুলো অনুসরণ করুন — বারবার অনুমতি না চেয়ে, প্রতিবার এই একই প্রক্রিয়া নিজে থেকেই মেনে চলুন।

**ধাপ ১ — Extract ও স্ক্যান করে বিভাগ চেনা**
- `.zip` unzip করে পেজ-সংখ্যা ও ক্রম যাচাই করুন।
- সবগুলো পেজ একবার দ্রুত `view` করে দেখুন কোন পেজে কোন বিভাগ আছে (এই ম্যাগাজিনে সাধারণত থাকে: দৈনিক ঘটনাপ্রবাহ+টপ নিউজ, MCQ, প্রশ্নোত্তর, দিবস-প্রতিপাদ্য/অনন্তলোকে, পদক-পুরস্কার, রিপোর্ট-সমীক্ষা, বিশেষ ফিচার প্রবন্ধ, দেশ পরিক্রমা, ইত্যাদি — প্রতি সংখ্যায় বিভাগের সেট বদলাতে পারে)।
- ব্যবহারকারীকে সংক্ষেপে বিভাগ-তালিকা দেখিয়ে জিজ্ঞেস করুন এই সেশনে কোন বিভাগ(গুলো) যুক্ত করতে হবে (একসাথে ৪৫+ পেজ ধরার চেষ্টা করবেন না — বড় সোর্স হলে ধাপে ধাপে)।

**ধাপ ২ — OCR ও পেজ-বাই-পেজ যাচাই**
- প্রতিটা পেজ আলাদাভাবে `view` করে টেক্সট বের করুন এবং ব্যবহারকারীকে দেখান।
- মূল স্ক্যান কম-রেজোলিউশন/ঝাপসা হলে জুম-ইন, কনট্রাস্ট/শার্পনেস বাড়িয়ে (Python PIL দিয়ে quadrant-ভাগ করে) আবার পড়ার চেষ্টা করুন।
- **ব্যবহারকারীর অনুমোদনের আগে পরের পেজে যাবেন না** — প্রতিটা পেজ শেষে ব্যবহারকারীর সিদ্ধান্ত/ঠিক-আছে-কিনা জিজ্ঞেস করুন।
- ব্যবহারকারী যদি একই পেজের একটা স্পষ্ট (যেমন ফোনে তোলা) ছবি সরবরাহ করেন, সেটাকেই চূড়ান্ত সোর্স ধরে আগের অনুমান-ভিত্তিক পাঠ সংশোধন করুন।
- অস্পষ্ট/কাটা-পড়া অংশ থাকলে স্পষ্টভাবে ⚠️ চিহ্ন দিয়ে জানিয়ে দিন, নিজে থেকে অনুমান করে বসিয়ে দেবেন না।
- **কঠোর নিয়ম — ভুল কনটেন্ট কখনো push করা যাবে না:** কোনো নাম, সংখ্যা, তারিখ, পদবি বা তথ্য নিয়ে সামান্যতম অনিশ্চয়তা থাকলেও নিজে অনুমান করে সেটা ঠিক করে বা বসিয়ে এগিয়ে যাবেন না। বরং স্পষ্টভাবে ব্যবহারকারীকে প্রশ্ন করে নিশ্চিত হয়ে নিন (কী অংশ নিয়ে অনিশ্চিত, কেন, এবং সম্ভাব্য পাঠ কী কী হতে পারে তা জানিয়ে)। অনিশ্চিত অংশ ব্যবহারকারীর নিশ্চিতকরণ ছাড়া `git commit`/`push` করা যাবে না। "সম্ভবত ঠিক আছে" ধরনের অনুমান কখনো চূড়ান্ত কনটেন্ট হিসেবে repo-তে যাবে না।

**ধাপ ৩ — সঠিক গন্তব্যে বসানো**
- দৈনিক ঘটনাপ্রবাহ (তারিখ + বাংলাদেশ/আন্তর্জাতিক বুলেট) → `docs/ghotonaprobaho/`।
- টপ নিউজ (তারিখ + একটাই হাইলাইট লাইন) → `docs/top-news/`।
- **নতুন তারিখ-রেঞ্জ existing ফাইলের ঠিক পরে/সংলগ্ন হলে, নতুন ফাইল না বানিয়ে existing ফাইল `git mv` দিয়ে বর্ধিত রেঞ্জ-নামে rename করে তার ভেতরেই এন্ট্রি যোগ করুন** (যেমন `2026-04-25_2026-05-18.md` → `2026-04-25_2026-06-26.md`)। existing ফাইলের শেষ তারিখে নতুন সোর্স থেকে অতিরিক্ত বুলেট এলে, আগে ডুপ্লিকেট কিনা চেক করে সেই একই হেডিং-এর নিচে যোগ করুন, নতুন হেডিং বানাবেন না।
- প্রশ্নোত্তর, দিবস-প্রতিপাদ্য, পদক-পুরস্কার, রিপোর্ট-সমীক্ষা, ফিচার প্রবন্ধ ইত্যাদির জন্য এখনো কোনো প্রমিত কাঠামো নেই — এগুলো নিয়ে আগানোর আগে ব্যবহারকারীর সাথে গন্তব্য (existing টপিক ফাইল আপডেট? নতুন টপিক? সম্পূর্ণ নতুন `docs/`-কাঠামো?) ঠিক করে নিন। (MCQ-এর জন্য নিয়ম নিচে "MCQ হ্যান্ডলিং" সেকশনে নির্দিষ্ট করা আছে — ওখানে আর জিজ্ঞেস করার দরকার নেই।)
- নতুন কোনো টপিক ঘটনাপ্রবাহে উল্লেখ হলে সেটা কোনো existing `docs/topics/*.md`-এর বিষয়ের সাথে মেলে কিনা যাচাই করুন (`[[phrase|slug]]` লিংক করার সুযোগ থাকতে পারে, কিন্তু ভুল slug হলে build ভাঙবে বলে সতর্ক থাকুন)।

**ধাপ ৪ — ভ্যালিডেট, কমিট, এবং নতুন branch-এ পুশ করে PR খোলা**

⚠️ **কখনো সরাসরি `main`-এ push করবেন না।** ব্যবহারকারী একই সাথে একাধিক Claude account/চ্যাট থেকে এই রিপোতে কাজ করেন — সরাসরি push করলে একজনের কাজ আরেকজনের কাজ না দেখেই সংঘর্ষ/ওভাররাইট হয়ে যেতে পারে। তাই প্রতিটা সেশন নিজের আলাদা branch-এ কাজ শেষ করে একটা Pull Request (PR) খোলে — main-এ merge (লাইভ) হওয়ার আগে PR-টাই "অপেক্ষার ঘর"। সম্পূর্ণ প্রক্রিয়া নিচের **"PR-ভিত্তিক ওয়ার্কফ্লো"** সেকশনে বিস্তারিত আছে; সংক্ষেপে:

1. `bash scripts/preflight.sh` চালান (`main`-এর বদলে বর্তমান branch-এর ভিত্তিতে build+verify পাস কিনা লোকালি নিশ্চিত করতে)।
2. `git diff` দেখিয়ে ব্যবহারকারীর অনুমোদন নিন কমিট করার আগে।
3. অনুমোদন পেলে বাংলায় স্পষ্ট, বিস্তারিত commit message লিখে কমিট করুন।
4. একটা নতুন branch পুশ করে (main না) GitHub API দিয়ে PR খুলুন — কমান্ড নিচের সেকশনে।
5. ব্যবহারকারীকে PR নম্বর ও কী বদলেছে সহজ ভাষায় জানান (নিজে ব্যাখ্যা করুন — raw diff দেখাবেন না)। GitHub-এর স্বয়ংক্রিয় চেক (build/verify/সংঘর্ষ) শেষ হতে ~১ মিনিট লাগে।
6. **ব্যবহারকারী স্পষ্টভাবে "মার্জ করো" না বলা পর্যন্ত merge করবেন না** — সব চেক পাস করলেও না। এটাই ব্যবহারকারীর চাওয়া "শেষ ক্লিক" ধাপ।
7. নতুন কোনো স্থায়ী সম্পাদকীয় সিদ্ধান্ত এলে `EDITORIAL_MEMORY.md`-এ টুকে রাখুন — অনুমতি না চেয়েই, কনভেনশন অনুযায়ী।

## MCQ হ্যান্ডলিং (স্থায়ী নিয়ম)

ম্যাগাজিনে MCQ সেকশন পেলে তিনটা কাজ করুন — **এই নিয়ম নিয়ে ব্যবহারকারীকে আর জিজ্ঞেস করার দরকার নেই, প্রতিবার সরাসরি অনুসরণ করুন।**

**১. Raw আর্কাইভ + সাইটের ইন্টারেক্টিভ কুইজের ডেটা-সোর্স (একই ফাইল, দুই কাজ):**
- `docs/mcq/` ফোল্ডারে `docs/ghotonaprobaho/`-র প্যাটার্ন অনুসরণ করে তারিখ/সংখ্যা-রেঞ্জ ভিত্তিক ফাইল বানান (যেমন `docs/mcq/2026-07.md`)।
- **এই ফাইলটাই সরাসরি সাইটের "📝 MCQ" ট্যাবের ডেটা-সোর্স** (`scripts/build_index.py`-র `parse_mcq_file()`/`compile_mcq()` এটা পার্স করে `docs/mcq-index.json` বানায়, যেটা `docs/index.html`-এর ইন্টারেক্টিভ কুইজ রেন্ডার করে) — তাই ফরম্যাট নিচের প্যাটার্ন **হুবহু** মানতে হবে, নয়তো প্রশ্ন পার্স হবে না ও কুইজে দেখাবে না:
  ```
  ## বিভাগের নাম
  ১. প্রশ্নের টেক্সট...
  ক) অপশন১ খ) অপশন২ গ) অপশন৩ ঘ) অপশন৪

  **উত্তর:** ১.গ ২.ক ...
  ```
- existing ফাইলের রেঞ্জ সংলগ্ন হলে নতুন ফাইল না বানিয়ে `git mv` দিয়ে rename করে ভেতরে যোগ করুন।
- পুরো MCQ সেট (প্রশ্ন + বিভাগ + উত্তর-কী) ম্যাগাজিনে যেভাবে আছে, প্রায় হুবহু সংরক্ষণ করুন। অনিশ্চিত/অস্পষ্ট উত্তর-কী নিয়ে সন্দেহ থাকলে ⚠️ নোট দিন কিন্তু মূল উত্তর-কী অবিকৃত রাখুন (নিজে থেকে সংশোধন করবেন না)।

**২. প্রাসঙ্গিক টপিকে ম্যানুয়াল merge (প্রতিটা প্রশ্ন যাচাই করে, স্ক্রিপ্ট দিয়ে না):**
- প্রতিটা প্রশ্নের অন্তর্নিহিত তথ্য নিয়ে আলাদা সিদ্ধান্ত নিন:

  - না থাকলে, এটা কোন existing টপিকে থিম্যাটিকভাবে ফিট করে খুঁজে বের করুন (পুরো `docs/topics/` লিস্ট দেখে) এবং সেখানে নতুন তথ্য হিসেবে যোগ করুন, "পরিবর্তনের ইতিহাস"-এ এন্ট্রি দিয়ে।
  - কোনো উপযুক্ত টপিক না থাকলে এবং তথ্যটা গুরুত্বপূর্ণ/স্বতন্ত্র মনে হলে, ব্যবহারকারীর সাথে নতুন টপিক বানানো উচিত কিনা জিজ্ঞেস করুন — ছোট/সামান্য তথ্যের জন্য নিজে থেকে নতুন টপিক ফাইল বানাবেন না।
- **এই merge প্রক্রিয়া কখনো স্বয়ংক্রিয় স্ক্রিপ্ট/regex/প্যাটার্ন-ম্যাচিং দিয়ে করবেন না** — কোন তথ্য কোথায় বসবে তা বিচার-বিবেচনার কাজ; ভুল জায়গায় বসানোর বা ডুপ্লিকেট তৈরির ঝুঁকি আছে বলে প্রতিবার নিজে পড়ে/বুঝে সিদ্ধান্ত নিন।

## উচ্চ-সংবেদনশীল / ঘন-পরিবর্তনশীল টপিক (বিশেষ সতর্কতা প্রয়োজন)

## গুরুত্বপূর্ণ সতর্কতা (এই রিপোতে আগে যা ভুল হয়েছিল)

> **🔒 সর্বোচ্চ-অগ্রাধিকার নীতি (২০২৬-০৮-১১, ব্যবহারকারীর নির্দেশ — কঠোরভাবে মেনে চলতে হবে):** কম টোকেন খরচ করা গুরুত্বপূর্ণ, কিন্তু ভুল ঠেকানো তার চেয়ে বেশি গুরুত্বপূর্ণ। **যেখানে ভুল হলে সত্যিকারের ক্ষতি হয়** (কনটেন্ট হারানো, ভুল তথ্য লাইভ হওয়া, একজনের কাজ আরেকজনের কাজ মুছে ফেলা/সংঘর্ষ) — **সেখানে কখনো টোকেন/খরচ বাঁচানোর জন্য কম যাচাই করবেন না, শর্টকাট নেবেন না।** টোকেন-সাশ্রয়ের চিন্তা শুধু সেইসব জায়গায় প্রযোজ্য যেখানে ভুল হলে বড়জোর অসুবিধা হয়, ক্ষতি না (যেমন: AI-সারাংশর মতো বাড়তি সুবিধা বাদ দেওয়া, সহজ conflict নিজে মিলিয়ে নেওয়া)। কোনো পরিস্থিতিতে "নিরাপদ কিন্তু বেশি টোকেন" বনাম "সস্তা কিন্তু ঝুঁকিপূর্ণ" — এই দ্বিধা এলে নিজে থেকে সস্তা পথ ধরে নেবেন না; ব্যবহারকারীকে স্পষ্টভাবে দুই বিকল্প জানিয়ে জিজ্ঞেস করুন।

1. **রিপোর history নিয়ে কোনো দাবি করার আগে সম্পূর্ণ (non-shallow) clone নিশ্চিত করুন।** `git clone --depth 1` বা কোনো shallow clone দিয়ে পুরনো কমিট মিস হয়ে যেতে পারে, যা থেকে ভুল সিদ্ধান্তে পৌঁছানো সহজ (এই রিপোতেই এমন ঘটনা ঘটেছিল — একটা AI shallow clone দেখে ভুলভাবে দাবি করেছিল একটা ফাইল "কখনোই ছিল না", যেখানে আসলে সেটা মুছে ফেলা হয়েছিল)। যাচাই করতে: `git rev-parse --is-shallow-repository` → `false` হওয়া উচিত। কমিট হ্যাশ/দাবি verify করতে `git log --all --oneline -- <path>` এবং `git merge-base --is-ancestor <sha> origin/main` ব্যবহার করুন।
2. **অন্য কোনো AI বা আগের চ্যাটের দাবি সরাসরি বিশ্বাস না করে নিজে git history/ফাইল চেক করে যাচাই করুন।** একাধিক AI ইনস্ট্যান্স একই রিপো নিয়ে ভিন্ন ভিন্ন (এমনকি পরস্পরবিরোধী) সিদ্ধান্তে পৌঁছাতে পারে — সবসময় নিজে সরাসরি verify করাই একমাত্র নির্ভরযোগ্য পথ।
3. **রিপো পাবলিক** — শুধু পড়তে/clone করতে কোনো টোকেন লাগে না। Push করতে টোকেন লাগবে, এবং `.github/workflows/`-এর ভেতরের ফাইল add/edit/push করতে টোকেনে আলাদাভাবে "workflow" স্কোপ/পারমিশন লাগে (শুধু "repo" স্কোপ যথেষ্ট নাও হতে পারে)। **PR-ভিত্তিক ওয়ার্কফ্লোর জন্য টোকেনে (fine-grained হলে) "Contents: Read and write" ও "Pull requests: Read and write" — দুইটাই লাগবে** (branch push + PR তৈরি/লিস্ট/মার্জ করার জন্য); নিছক push-only টোকেন দিয়ে PR খোলা/মার্জ করা যাবে না।
4. **`CHANGELOG.md`-এ মাসিক কনটেন্ট আপডেট লিখবেন না** — শুধু সিস্টেম-লেভেল পরিবর্তন (ফিচার, ডিজাইন, ফাইল-কাঠামো)। কনটেন্ট আপডেটের ইতিহাস প্রতিটা টপিক ফাইলের নিজের "পরিবর্তনের ইতিহাস" টেবিলে থাকে।
5. **কোনো মেজর/সিস্টেম-লেভেল পরিবর্তনের আগে ব্যবহারকারীর অনুমতি নিন**, এবং অনুমতি পেলে `CHANGELOG.md`-এ এন্ট্রি যোগ করুন ও প্রয়োজনে `VERSION` বাড়ান।
6. **একাধিক Claude সেশন/অ্যাকাউন্ট থেকে একই সাথে এই রিপোতে কাজ করা হয় — এটা এখন স্বাভাবিক অবস্থা, edge case নয়। ঠিক এই কারণেই ২০২৬-০৮ থেকে সরাসরি `main`-push বাদ দিয়ে branch+PR মডেল চালু হয়েছে** (দেখুন "PR-ভিত্তিক ওয়ার্কফ্লো" সেকশন — এই নিয়ম চালু হওয়ার ঠিক আগমুহূর্তেই আরেকটা সেশন সরাসরি `main`-এ পুশ করে ফেলেছিল, যা থেকেই এই নিয়মের প্রয়োজনীয়তা আরও স্পষ্ট হয়)। দুইটা চেকপয়েন্ট মনে রাখুন:
   - **কাজ শুরুতে**: `bash scripts/session_status.sh` — বাস্তব অবস্থায় re-orient করার জন্য, কিছু ব্লক করে না।
   - **নিজের branch পুশ করার আগে**: `bash scripts/preflight.sh` চালান — build+verify পাস করছে কিনা লোকালি নিশ্চিত করতে। build/verify ব্যর্থ হলে সেই এরর ঠিক না করে push করবেন না।
   - **branch push ও PR তৈরির পর**, বাকি সংঘর্ষ-শনাক্তকরণ (অন্য কোনো খোলা PR একই ফাইলে হাত দিয়েছে কিনা) GitHub Actions (`pr-check.yml`) স্বয়ংক্রিয়ভাবে করে — নিজে থেকে rebase/force-push করে সমাধান করার দরকার নেই, PR-এর কমেন্টে সমস্যা দেখানো হবে।
   - PR-এর নিজের branch-এ (কখনো `main`-এ না) দরকার হলে সাধারণ `git push` ব্যবহার করুন; `--force`/`--force-with-lease` তখনই ঠিক আছে যদি সেই branch-এ শুধু আপনার নিজের এই সেশনের কমিটই থাকে (অন্য কেউ সেই একই branch-এ push করেনি)। **branch protection চালু হওয়ার পর `main`-এ সরাসরি push এমনিতেই GitHub প্রত্যাখ্যান করবে — কিন্তু তার আগেও এই নিয়ম মেনে চলুন।**
   - **যদি কখনো `main` protection সাময়িকভাবে বন্ধ থাকা অবস্থায় কোনো সেশন ভুলবশত সরাসরি `main`-এ পুশ করে ফেলে** (ঠিক যেমনটা এই নিয়ম চালুর মুহূর্তেই ঘটেছিল): নিজের চলতি branch-এ `git rebase origin/main` চালান। Conflict এলে নিচের নিয়ম অনুযায়ী।
7. **rebase-এ conflict এলে নিজে অনুমান করে কোনদিকের পরিবর্তন রাখবেন তা ঠিক করবেন না।** conflict-এ থাকা ফাইল ও উভয় পক্ষের পরিবর্তন ব্যবহারকারীকে স্পষ্টভাবে দেখিয়ে জিজ্ঞেস করুন — **ব্যতিক্রম**: যদি দুই পক্ষের পরিবর্তন সত্যিকারের বিষয়বস্তু-দ্বন্দ্ব না হয়ে শুধু একই জায়গায় ভিন্ন ভিন্ন নতুন সংযোজন হয় (যেমন একই টেবিলে দুই সেশনের আলাদা নতুন row, বা CHANGELOG-এ দুই সেশনের আলাদা নতুন এন্ট্রি) — তখন দুটোই রেখে (তারিখ/ভার্সন অনুযায়ী সাজিয়ে) নিজে মিলিয়ে নেওয়া ঠিক আছে, ব্যবহারকারীকে জিজ্ঞেস করার দরকার নেই। Auto-generated ফাইলে (`docs/topics-index.json`, `docs/sw.js`, `docs/version.json` ইত্যাদি) conflict এলে হাতে এডিট না করে rebase-এর পরে `python3 scripts/build_index.py` চালিয়ে ফের জেনারেট করাই সঠিক পথ।
8. **কোনো নতুন bug পাওয়া/ঠিক করা হলে, শুধু `BUGFIX.md`-এ এন্ট্রি লিখেই থামবেন না — `scripts/test_build_index.py` বা `scripts/js_tests/run.mjs`-এ একটা matching automated regression test যোগ করুন**, যাতে ঠিক এই bug-টা future কোনো feature/refactor-এ চুপচাপ আবার ফিরে না আসে (`preflight.sh` প্রতি push-এ এগুলো চালায়)। শুধু ডকুমেন্টেশনে লেখা "ঠিক করা হয়েছে" যথেষ্ট নয় — আসল কোডে ফিক্সটা সত্যিই আছে কিনা টেস্ট না থাকলে ভবিষ্যতে কেউ (মানুষ বা AI) যাচাই না করেই ধরে নেবে। bug-টা যদি real browser rendering/layout সংক্রান্ত হয় (jsdom দিয়ে ধরা কঠিন), অন্তত `TEST_CHECKLIST.md`-এ একটা লাইন যোগ করুন এবং কেন automated test সম্ভব হলো না তা `BUGFIX.md` এন্ট্রিতে লিখে রাখুন।

## PR-ভিত্তিক ওয়ার্কফ্লো (একাধিক সমান্তরাল সেশনের জন্য, ২০২৬-০৮ থেকে বাধ্যতামূলক)

ব্যবহারকারী একই সাথে একাধিক Claude account/চ্যাট থেকে এই রিপোতে কাজ করান। তাই `main`-এ সরাসরি push না করে, প্রতিটা সেশন নিজের branch-এ কাজ শেষ করে PR খোলে; GitHub স্বয়ংক্রিয়ভাবে গঠন ও সংঘর্ষ চেক করে; সেই PR-এর পরিবর্তন যে সেশনেই জিজ্ঞেস করা হোক না কেন Claude নিজে পড়ে সহজ বাংলায় ব্যাখ্যা করে; **ব্যবহারকারী নিজে সেটা শুনে "মার্জ করো" বললেই তবে merge হয়** — নাহলে না। নিচে ধাপে ধাপে কমান্ড।

**(সিদ্ধান্ত, ২০২৬-০৮-১১):** এই "merge-অনুমোদন" অংশটা GitHub-এর নিজস্ব "approve" ফিচার দিয়ে প্রযুক্তিগতভাবে বাধ্যতামূলক করা সম্ভব ছিল (তাহলে ব্যবহারকারীর স্পষ্ট অনুমতি ছাড়া merge বাটনই সক্রিয় হতো না)। কিন্তু তার জন্য একটা দ্বিতীয় GitHub অ্যাকাউন্ট লাগত (নিজের PR নিজে approve করা যায় না) এবং প্রতি merge-এ বাড়তি সমন্বয়/টোকেন খরচ হতো। ব্যবহারকারী কম-খরচের বিকল্প বেছে নিয়েছেন — তাই এই অংশটা এখনো এই লিখিত নিয়মের ওপর নির্ভরশীল, GitHub প্রযুক্তিগতভাবে বাধ্য করে না। **এটা মূল উদ্বেগ (সংঘর্ষ/সরাসরি-পুশ প্রতিরোধ) থেকে সম্পূর্ণ আলাদা** — সেটা branch protection দিয়ে সম্পূর্ণ প্রযুক্তিগতভাবেই বাধ্যতামূলক, এই সিদ্ধান্তে তার কোনো হেরফের নেই।

**(সিদ্ধান্ত, ২০২৬-০৮-১২): কম-ঝুঁকির PR-এ auto-merge, বাকি সব PR-এ আগের নিয়মই বহাল।** প্রতিটা PR-এ "মার্জ করো" শোনার জন্য অপেক্ষা করা ব্যবহারকারীর জন্য কিছুটা ক্লান্তিকর মনে হওয়ায় এই দুই-স্তরের নিয়ম চালু হয়েছে:

- **Auto-merge (অনুমতি ছাড়াই merge, শুধু ফলাফল জানিয়ে দিন) — নিচের সবগুলো শর্ত সত্যি হলেই:**
  1. শুধু নতুন কনটেন্ট **সংযোজন** (নতুন টপিক/MCQ/ঘটনাপ্রবাহ/টপ-নিউজ এন্ট্রি) — কোনো existing কনটেন্ট মোছা বা বদলানো (edit/replace/delete) নেই।
  2. `AGENTS.md`, কোনো `scripts/*`, বা `.github/workflows/*` ছোঁয়া হয়নি — বিশুদ্ধ কনটেন্ট-ফাইল পরিবর্তন (`docs/topics/`, `docs/ghotonaprobaho/`, `docs/top-news/` ইত্যাদি)।
  3. `preflight.sh` ক্লিন পাস করেছে।
  4. GitHub-এর স্বয়ংক্রিয় PR-চেক (`pr-check.yml`) কোনো সমস্যা/কমেন্ট দেয়নি এবং `mergeable: true`।
  
  এই শর্তগুলো পূরণ হলে ধাপ ৬-এ না গিয়ে সরাসরি merge করুন, তারপর ব্যবহারকারীকে সংক্ষেপে জানান কী merge হলো।

- **আগের নিয়মই বহাল (এখনো স্পষ্ট "মার্জ করো" শোনা বাধ্যতামূলক) — নিচের যেকোনো একটা সত্যি হলে:**
  1. `AGENTS.md`, কোনো `scripts/*`, বা `.github/workflows/*`-এ বদল (নিয়ম/কোড/অটোমেশন পরিবর্তন)।
  2. কোনো existing কনটেন্ট মোছা বা replace করা হয়েছে।
  3. কোনো rebase-conflict নিজে সমাধান (item 7-এর ব্যতিক্রম বাদে বাকি সব ক্ষেত্রে) করা হয়েছে এমন PR।
  4. স্বয়ংক্রিয় চেক কোনো সমস্যা/কমেন্ট দিয়েছে, বা `mergeable` `true` না।
  5. যেকোনো সন্দেহ/দ্বিধা থাকলে — নিরাপদ দিকে থেকে অনুমতি চাওয়াই সঠিক পথ (উপরের "🔒 সর্বোচ্চ-অগ্রাধিকার নীতি" অনুযায়ী)।

**টোকেন-ব্যবহারের নিয়ম অপরিবর্তিত:** ব্যবহারকারীর দেওয়া অস্থায়ী PAT `http.extraheader`-এ শুধু চলতি কমান্ডের জন্য বসান (কখনো `git remote set-url`-এ না, `.git/config`-এ যেন থেকে না যায় তা প্রতিটা push/API-কলের পর `grep -i authorization .git/config` বা সমতুল্য দিয়ে যাচাই করুন)। এবারের PAT-এ শুধু "Contents" না, **"Pull requests" স্কোপও লাগবে** (branch push, PR তৈরি/লিস্ট/মার্জ — চারটাই)।

**১. নিজের branch বানানো ও কাজ করা**
```bash
git checkout -b work/2026-08-11-short-topic-slug   # তারিখ + সংক্ষিপ্ত-বিষয়
# ... এডিট ...
bash scripts/preflight.sh   # build+verify পাস কিনা লোকালি নিশ্চিত করুন
git add -A && git commit -m "বাংলায় স্পষ্ট বার্তা"
```

**২. branch পুশ করা (main না, নিজের branch)**
```bash
git -c http.extraHeader="Authorization: Bearer $PAT" push origin work/2026-08-11-...
```

**৩. PR খোলা**
```bash
curl -s -X POST \
  -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/openjobsolutionbd/open_current_affairs/pulls \
  -d '{"title":"সংক্ষিপ্ত বাংলা শিরোনাম","head":"work/2026-08-11-...","base":"main","body":"কী বদলেছে — বাংলায় ২-৩ লাইন"}'
```
রেসপন্সের `"number"` ফিল্ডটাই PR নম্বর — ব্যবহারকারীকে সেটা জানান।

**৪. ব্যবহারকারীকে জানানো (এই ধাপেই preflight-এর মতো টেকনিক্যাল আউটপুট কপি করবেন না)** — উপরের "auto-merge" শর্ত সব পূরণ না হলে বলুন: "PR #N খোলা হয়েছে — [সহজ ভাষায় কী বদলেছে]। স্বয়ংক্রিয় চেক শেষ হতে ~১ মিনিট লাগবে। মার্জ করব?" — auto-merge-যোগ্য PR হলে চেক পাস হওয়ার পর সরাসরি merge করে শুধু জানিয়ে দিন কী merge হলো, অনুমতি চাইবেন না।

**৫. যেকোনো সেশনে "কী কাজ পেন্ডিং আছে" জিজ্ঞেস করলে — সব খোলা PR দেখানো**
```bash
curl -s -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  "https://api.github.com/repos/openjobsolutionbd/open_current_affairs/pulls?state=open"
```
প্রতিটার আসল পরিবর্তন দেখতে (raw diff পাওয়া যায়, `.diff` ফরম্যাটে):
```bash
curl -s -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github.v3.diff" \
  "https://api.github.com/repos/openjobsolutionbd/open_current_affairs/pulls/<PR_NUMBER>"
```
স্বয়ংক্রিয় চেক কোনো সমস্যা পেলে সেটা কমেন্ট আকারে থাকে (দেখুন `pr_checks.py`):
```bash
curl -s -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  "https://api.github.com/repos/openjobsolutionbd/open_current_affairs/issues/<PR_NUMBER>/comments"
```
diff নিজে পড়ে ব্যবহারকারীকে সহজ বাংলায় জানান (কোন টপিকে কী যোগ/বদল হলো) — raw diff/JSON কখনো সরাসরি দেখাবেন না।

**৬. ব্যবহারকারী "মার্জ করো" বললে — তবেই merge**
```bash
curl -s -X PUT \
  -H "Authorization: Bearer $PAT" -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/openjobsolutionbd/open_current_affairs/pulls/<PR_NUMBER>/merge \
  -d '{"merge_method":"squash"}'
```
merge ব্যর্থ হলে (checks এখনো শেষ হয়নি, বা conflict) response-এর `"message"` পড়ে ব্যবহারকারীকে সহজ ভাষায় জানান, নিজে থেকে force করার চেষ্টা করবেন না।

**৭. merge সফল হলে branch মুছে ফেলুন (পরিষ্কার রাখতে)**
```bash
curl -s -X DELETE -H "Authorization: Bearer $PAT" \
  https://api.github.com/repos/openjobsolutionbd/open_current_affairs/git/refs/heads/work/2026-08-11-...
```
merge-এর পর `main`-এ push হওয়ার কারণে `.github/workflows/update-wiki.yml` নিজে থেকেই generated output রিবিল্ড করে দেবে — সেটা আলাদা করে করতে হবে না।

**যদি PR-এ real git conflict দেখায়** (দুইটা branch একই লাইনে ভিন্ন পরিবর্তন করেছে — GitHub-এর `mergeable: false`): নিজে অনুমান করে কোনটা রাখবেন ঠিক করবেন না, উপরের item 7-এর ব্যতিক্রম-নিয়ম মেনে চলুন। Auto-generated ফাইলে conflict কখনো হাতে মার্জ করবেন না — merge-এর পর `main`-এ `build_index.py` এমনিতেই আবার চালাবে।
